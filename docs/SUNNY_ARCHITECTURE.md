# Sunny architecture – approved direction, technical contracts pending review
Sunny is an independent, local-first, learning-capable modular assistant. MeinHelfer remains the first host, not a replacement target.
Core: request/context/orchestrator/response; deterministic routing and offline fallback; replaceable local runtime; memory and feedback interfaces; module registry; host adapters. Guard mediates all data access, network and actions, independently of model suggestions. Deny by default. No direct DB access from modules. Long-term memory opt-in, encrypted, scoped to user/person, inspectable, correctable, deletable and exportable. No automatic permission escalation. Hybrid processing requires explicit consent and data minimization. Generated modules start declarative, isolated, reviewed and approved; no arbitrary code execution.
Preserve existing routing, SunnyLocalEngine, phrasebook, preferences, Steuerwerk (3 accepts offer, 3 declines with no accepts pause 7 days), mood policy, capability metadata and action guard. Preserve all existing app features and avatar identity, SU01–35 media, image/video/auto modes, foreground speech, design options, offline help, motivation opt-in and quiet mode. Future extensions: SU36+, Emotion Studio, voice control, app adapters and separately authorized cross-app assistance.
Target modules: sunny-core (pure JVM), sunny-runtime-android, sunny-modules, sunny-connect, sunny-standalone. Introduce incrementally. Existing app remains intact.
Reference: project chats 00–14 and Brain/Reaction Matrix pages; detailed requirements reconciliation remains pending. No claim of exhaustive inventory.

## Capability ownership – owner-approved 2026-11-27
All existing and future MeinHelfer AI capabilities follow the core/module split in ROADMAP-2026-11-27.md: reusable app-independent capabilities belong directly in Sunny's general capability layer; MeinHelfer-specific capabilities belong in its dedicated module via Sunny Connect. Preserve existing behavior until tested replacement and separate acceptance. The module must not bypass app data ownership or Guard. Promotion of reusable capabilities requires review and tests, never automatic permission expansion.
